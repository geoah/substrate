# The Apple apps

The console, bundled, in a native shell for macOS, iPadOS and iOS: one
SwiftUI target (`Substrate`, bundle id `dev.reamde.substrate.console`) that
builds natively for both SDKs, not Mac Catalyst. The app carries its own copy
of `web/console/dist` and talks to a substrate only through its API, so any
substrate the user can reach works, whatever console that server serves.

```bash
mise run apple:install       # console + macOS app, installed in /Applications and opened
mise run apple:sim           # console + iOS app, on a booted (or the first) iPhone simulator
mise run apple:build         # console + the macOS app + the iOS simulator app
mise run apple:build:device  # console + the iOS app for a device, signed for the team's devices
mise run apple:project       # regenerate Substrate.xcodeproj, to open it in Xcode
mise run apple:release       # console + both apps, signed and published with their update feeds
```

The project file is generated by [xcodegen](https://github.com/yonaskolb/XcodeGen)
from `project.yml` and never committed. Signing is Xcode's automatic signing
for team `KFA5J8GDWJ`; the builds use the Apple Development identity and the
account signed in to Xcode, which `-allowProvisioningUpdates` registers the
app id and the device profile with. Nothing here runs in CI.

## How the console runs in it

The console only ever asks for same-origin paths, because the server serves
it at `/` with the API beside it. The shell keeps that true:
`ConsoleSchemeHandler` serves the bundled build at `substrate://console/` and
forwards the substrate's own paths (`/api/`, `/.well-known/`, `/healthz`, and
the auth door at the root when the request is not a navigation) to the chosen
server with `URLSession`, chunk by chunk, so the changefeed and an agent's turn
stream as they do in a browser. The server needs no CORS and the console no
base URL.

| Concern         | What the shell does                                                                     |
| --------------- | --------------------------------------------------------------------------------------- |
| Which server    | A native picker checks the address's discovery document first; the choice is remembered |
| Sessions        | One website data store per server: its token and console state stay with it             |
| The page's view | `window.substrateShell` (`{platform, server}`) is set before any script runs            |
| Links           | Anything outside `substrate://` opens in the system browser                             |
| `window.open`   | A provider's OAuth consent opens in the system browser, and its return lands there too  |
| Downloads       | The export lands in Downloads (macOS) or a share sheet (iOS)                            |
| macOS menus     | Change Server (⇧⌘,), Reload (⌘R), zoom (⌘0, ⌘+, ⌘−), Back and Forward (⌘[, ⌘])          |

The console's side is `web/console/src/lib/shell.ts`: the substrate's origin
and host come from the shell when there is one (a pasted record link, a bare
repository label completed at registration), the sign-in and register pages
name the server with a Change link, and Settings has a Server row. In a
browser there is no shell and none of it renders.

The macOS release build is sandboxed (`Support/Substrate-macOS.entitlements`:
network client, Downloads) with the hardened runtime. The debug build runs
outside the sandbox, for the driver below.

## Releases and updates

`mise run apple:release` (a pre-release; `apple:release stable` for a stable
one, from a clean tree) archives both apps, exports them, and publishes them
to `SUBSTRATE_APPLE_RELEASE_URL`: the path-style address of a folder on an S3
bucket that anyone may read and the key in `AWS_ACCESS_KEY_ID` /
`AWS_SECRET_ACCESS_KEY` may write. The address names a deployment, so it comes
from the environment, never from this tree.

```bash
SUBSTRATE_APPLE_RELEASE_URL=https://s3.example.com/public/projects/substrate/apple \
AWS_ACCESS_KEY_ID=… AWS_SECRET_ACCESS_KEY=… mise run apple:release
```

The version is the next patch after the last released one, plus the build
number and the commit, `0.113.1-pre.20261021.153012+ac85863e` (`.dirty`
when the tree was); the build number is the UTC time, so it only rises, and
it is what one release is compared to another by. The folder holds:

| Path                | What                                                                    |
| ------------------- | ----------------------------------------------------------------------- |
| `index.json`        | Every release, newest first; what the iOS app reads                     |
| `appcast.xml`       | Sparkle's feed; pre-releases ride its `prerelease` channel              |
| `index.html`        | The install page: an iPhone installs from it in Safari, a Mac downloads |
| `releases/<build>/` | The macOS zip, the IPA, its install manifest and icons, `release.json`  |

A released build carries the folder's address; a local build carries none
and never looks. On macOS, Sparkle checks at every launch, every four hours
after and on Substrate → Check for Updates, verifies the archive against the
EdDSA key made on the first release (kept in the login keychain under
`substrate`; losing it means every installed Mac app is replaced by hand once)
and installs it. On iOS only the system may install an app: the app reads
`index.json` at launch and when it comes to the foreground, at most hourly,
and offers the newer release's install link. Both include pre-releases when
the running build is one; the Mac's app menu turns that off. On both, the
console's Settings → Signed in shows the app's version with a Check for
updates button, which asks the shell (`checkForUpdates` in
`web/console/src/lib/shell.ts`) to check now.

Provisioning goes through the Apple ID signed in to Xcode, a session that
expires and can only be renewed in Xcode's window. An App Store Connect API
key replaces it for a shell: set `SUBSTRATE_APPLE_ASC_KEY_PATH` (the
`AuthKey_….p8`), `SUBSTRATE_APPLE_ASC_KEY_ID` and
`SUBSTRATE_APPLE_ASC_ISSUER_ID`, and every build and export passes them to
`xcodebuild`. The key needs the Admin role, because registering an app id's
capabilities (Substrate Sync's HealthKit) is an admin's act. Like the release
address, it lives in the environment and never in the tree.

Both are signed with the team's Apple Development identity, so the IPA
installs on the devices in the team's development profile (with Developer
Mode on) and the Mac app opens after Privacy & Security → Open Anyway once.
`SUBSTRATE_APPLE_EXPORT_IOS=release-testing` and
`SUBSTRATE_APPLE_EXPORT_MACOS=developer-id` switch to ad hoc and Developer ID
signing once those certificates exist.

## Driving a debug build

A debug build carries `DebugDriver`: it watches `automation/` in the app's
temporary directory, runs an `eval.js` found there in the page as an async
function body and writes the answer to `result.json`, and answers a `snap`
file with `snap.png`, the web view's snapshot. `SUBSTRATE_SHELL_SERVER` in
the environment starts it pointed at a server, past the picker.

```bash
# macOS
SUBSTRATE_SHELL_SERVER=http://localhost:8080 \
  apps/apple/build/dd/Build/Products/Debug/Substrate.app/Contents/MacOS/Substrate &
dir="$(getconf DARWIN_USER_TEMP_DIR)automation"
echo 'return document.title' >"$dir/eval.js"; sleep 1; cat "$dir/result.json"

# a simulator: the app's data container
SUBSTRATE_SHELL_SERVER=http://localhost:8080 mise run apple:sim
dir="$(xcrun simctl get_app_container booted dev.reamde.substrate.console data)/tmp/automation"
```

Release builds carry none of it.

## Substrate Sync

A second app in the same project: `SubstrateSync` (bundle id
`dev.reamde.substrate.sync`), iPhone and iPad only, iOS 26. It carries no
console and no Sparkle. It reads the device's Health, Contacts, Calendar,
Reminders and the places it stays at, and pushes them into one repository,
signed in with the owner's password, over the API alone. Nothing is written
back to the device. Its share extension, Send to Substrate, saves what any
app shares.

```bash
mise run apple:build:sync     # the app for the simulator
mise run apple:release:sync   # archived, signed and published under sync/
```

| Source    | Lands as | How |
| --------- | -------- | --- |
| Contacts  | `providers.substrate.reamde.dev/apple/addressbook` and `…/contact` | `PUT` per changed contact, `PATCH` to null for a vanished key, `DELETE` for a vanished contact, then the address book row |
| Calendars | `…/apple/eventstore`, `…/calendar` and `…/event` | every event calendar and every occurrence from 90 days back to 180 ahead; an event that ages out of the window keeps its row |
| Reminders | `…/apple/reminderlist` and `…/reminder`, under the event store | every list and every reminder, completed ones too; a deleted one is removed |
| Places    | `…/apple/visitstore` and `…/visit` | the visits iOS reported while Places was on, kept a year on the phone, named by Apple Maps |
| Health    | `providers.substrate.reamde.dev/applehealth` mirror rows, then observations, sleep and workouts through the provider's own adapter, under `substrate.reamde.dev` | Health Auto Export's JSON to `/webhooks/<authority>/applehealth-webhook`, two deliveries per local day |
| Shares    | `…/apple/share`, the images as blobs | the share extension, once per share |

The ids and the field rules are the apple package's
[README](../../kinds/providers.substrate.reamde.dev/apple/README.md); the
Health format is the one `internal/synth/applehealth.go` emits, and two
goldens hold the app to it from both sides:
`internal/providertest/testdata/applehealth/app_minutes.json` and
`app_seconds.json`. The app's tests compare its encoder with them byte for
byte, and `internal/providertest/substratesync_test.go` runs them through
the provider and the adapter. After a deliberate change to the format,
regenerate them and run both:

```bash
TEST_RUNNER_SUBSTRATE_UPDATE_GOLDEN=1 xcodebuild -project apps/apple/Substrate.xcodeproj \
  -scheme SubstrateSync -destination 'platform=iOS Simulator,name=iPhone 18 Pro' test
go test -count=1 -run TestSubstrateSync ./internal/providertest/
```

**Signing in** checks the address's discovery document, asks for a code only
when `registration.totpRequired` says so, and keeps the token's secret, its
id and the repository in the Keychain. Sign Out forgets them on the phone at
once and revokes the token in the background, so it works with the server
unreachable or the token already refused. A token the server refuses (the
repository was wiped, or the token revoked) stops every sync and shows one
screen whose button signs in again. What the phone remembers is bound to the
repository it was pushed to: signing in to another one, or finding the
contacts' address book, the calendar store or the Health account gone from
the server, sends everything again.

**Set up** lists what the repository lacks and does it with one button:
installs (or upgrades to version 3) `providers.substrate.reamde.dev/apple`
and installs (or upgrades to version 5) `…/applehealth`, which ships the
adapter and installs the `substrate.reamde.dev/health` catalogue it
requires; then it creates the Health account
`substrate-sync-<first 8 characters of the install id>`, and arms the
`applehealth-webhook` trigger. It keeps a key already on the trigger unless
the owner says to replace it, and otherwise sets a new 32-character one. A
refusal is shown in the server's own words.

**Health** goes as two deliveries per local day, oldest day first: every
metric at one row per minute (`automation-aggregation: minutes`), and the
sleep segments and workouts (`seconds`). The first sync sends the history
Health → History names (14 days unless it says 30 days, 3 or 6
months, a year, or everything the phone holds); each later one sends the last
three days again and any day not yet accepted. A day counts as sent only once
the server has filed it (its `applehealth/export/<fire id>` receipt); one the
server parked stays queued and is sent again. Days go seven at a time, and a
range longer than a month first asks HealthKit which days hold data, so years
of history are not read one empty day at a time. A background run sends only
the last three days. A delivery replaces a metric's rows across its span, so
a day is always sent whole, and a day larger than 4 MiB is split by metric.
Besides the measured metrics, a day carries what is logged: mindful minutes
(each session at the minute it starts), water and eleven nutrients, and basal
body temperature, which the adapter maps to the `health/*` metrics of those
names; cycle tracking, as the `cycleTracking` section (`cycleevent` rows); and
each workout's GPS route, thinned to 15,000 points, which stays on the
workout's mirror row.

**Reminders** are read whole each sync: every list (an `EKCalendar` for
reminders) and every reminder, with its due day, and its due moment where it
has a time. A list or a reminder gone from the phone is deleted, and an empty
answer from EventKit deletes nothing.

**Places** is off until it is turned on, because it asks for Always location
access. It uses iOS's visit monitoring, which reports a stay when the phone
arrives and again when it leaves, at little cost to the battery, and relaunches
the app in the background to do it. Each report is kept in a log on the phone
for a year; a sync names up to 25 new visits a run through MapKit's reverse
geocoder and sends them all, so a reset repository gets the year back. iOS
keeps no history of its own, so Places starts when it is turned on.

**Send to Substrate** is a share extension: a link, text and up to four
images from any app's share sheet, with a note, saved as one `share` record.
It reads the app's sign-in from the Keychain group the two share, uploads the
images as blobs and writes the record within the minute the server keeps an
unreferenced blob. A link shared again updates its record.

**Home is an overview.** A status card says what is syncing (the source,
its step and how far it has got, and Stop) or how the last sync ended, above
Sync Now. Each source is one row: what it has synced of what the phone holds,
when, and its state as a badge (Up to date, Syncing, Queued, Being filed,
Failed, No access, Off). A source that is running or waiting its turn shows
that, never the error of the run it is replacing. Tapping a source opens its
page: the state with the last run or its error and a button that syncs that
source alone, its coverage once (Health: the days with data inside the
history, those waiting for the server, those going at the next sync, a chart
grouped to fit the history, and every period a tap away; the days older than
the history are counted apart and sent on request), its settings (the
switch, access, Health's history, which calendars), and its last runs.
Activity is one timeline: each run with how it ended and how long it took,
its log lines folded inside it, filterable by source. The account, the
background frequency, the server set up, the version and Sign Out are behind
the gear.

**Calendars** sends the calendars turned on in Calendars → Calendars, by
account. The setting keeps the ones turned off, so a calendar added on the
phone later is sent until it is turned off; a calendar turned off is removed
from the repository, with its events, at the next sync, as one deleted on the
phone is.

**A day waiting for the server** keeps the fire ids of its deliveries, and
the next sync reads their receipts before it sends anything, so a day the
server filed since is not sent again.

**In the background** a refresh task syncs when the system allows, and
HealthKit's observer queries (heart rate, steps, sleep, workouts) wake the
app to send Health. Settings → Sync in the background picks hourly, every
six hours, daily, or only on Sync Now: it is the soonest a background run
may sync a source again, the refresh task's earliest start, and HealthKit's
delivery frequency (none when syncing by hand). iOS decides the moment. The debug build's Home has Add Sample
Data, which writes yesterday's Health samples, three contacts and a sample
calendar for a simulator to sync.

**Releases** go to `$SUBSTRATE_APPLE_RELEASE_URL/sync/`, a folder of their
own with the same `index.json`, install page and manifests (`feed.swift`
reads the app's `name` from `release.json`), and the app's Check for Updates
reads it. The build needs HealthKit on the development profile: with
automatic signing `-allowProvisioningUpdates` adds it to
`dev.reamde.substrate.sync`, else enable it on the identifier in the
developer portal. The IPA installs on the team's registered devices, with
Developer Mode on.

## Layout

```text
project.yml                 the xcodegen spec, the only project source
Support/                    Info.plist per platform and Substrate Sync's, the entitlements
Substrate/Assets.xcassets   the icon (scripts/icon.swift draws it)
Substrate/Sources/App/      the app, its macOS menus, ServerStore, the updater
scripts/feed.swift          a release's index.json, appcast.xml, install page and manifest
Substrate/Sources/Shell/    the scheme handler, the web view's controller, the picker, the debug driver
SubstrateSync/Sources/      Substrate Sync: App/, API/, Sync/ (the mappings, the readers, the engine), Views/, Debug/
SubstrateSyncTests/         its tests: ids, labels, dates, the Health goldens
```

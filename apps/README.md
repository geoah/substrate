# The apps

Five apps: the console in a native shell, Substrate Chat, Substrate Sync,
Substrate Workouts and Substrate Tasks (each below), all on Apple systems
and Tasks on Android too; and the template `mise run apps:new` copies, a
whole app that nothing releases ([A new app](#a-new-app)). Each is a folder
here named by its [app.json](#an-apps-appjson), six in all, beside the kit
they share ([kit/](kit/README.md)) and the two build roots, `xcode/` and
`gradle/`.

The console, bundled, in a native shell for macOS, iPadOS and iOS: one
SwiftUI target (`Substrate`, bundle id `dev.reamde.substrate.console`) that
builds natively for both SDKs, not Mac Catalyst. The app carries its own copy
of `web/console/dist` and talks to a substrate only through its API, so any
substrate the user can reach works, whatever console that server serves.

```bash
mise run apple:install       # console + macOS app, installed in /Applications and opened
mise run apple:sim           # console + iOS app, on a booted (or the first) iPhone simulator
mise run apple:build         # console + the macOS app + the iOS simulator app
mise run apple:build:device  # console + the iOS app for a device, signed for the team's devices
mise run apple:project       # regenerate Substrate.xcodeproj, to open it in Xcode
mise run apps:release        # every app with a UI, on every platform, signed and published with their feeds (below)
```

The project file is generated by [xcodegen](https://github.com/yonaskolb/XcodeGen)
from `xcode/project.yml`, which includes each app's `apple/targets.yml`, and
is never committed. Signing is Xcode's automatic signing
for the team `xcode/project.yml` names; the builds use the Apple Development identity and the
account signed in to Xcode, which `-allowProvisioningUpdates` registers the
app id and the device profile with. CI builds no Apple app: its `apps linux`
job builds and tests the kit and every app's core on Linux, then the core of
an app `apps:new` makes, and its `android build` job builds the kit for
Android ([Android](#android)); the SwiftUI side is a Mac's, through the
`apple:test:*` tasks.

## How the console runs in it

The console only ever asks for same-origin paths, because the server serves
it at `/` with the API beside it. The shell keeps that true:
`ConsoleSchemeHandler` serves the bundled build at `substrate://console/` and
forwards the substrate's own paths (`/api/`, `/.well-known/`, `/healthz`, and
the auth door at the root when the request is not a navigation) to the chosen
server with `URLSession`, chunk by chunk, so the changefeed and an agent's turn
stream as they do in a browser. The server needs no CORS and the console no
base URL.

| Concern         | What the shell does                                                                     |
| --------------- | --------------------------------------------------------------------------------------- |
| Which server    | SubstrateKit's connect screen, as in Chat and Sync: the address, checked against its discovery document and OAuth metadata; Change Server opens it over the console |
| Signing in      | The kit's app authorization asking for `full` (decision 0204): the server's own page in Safari's sheet (the default browser on a Mac). A server without `full` hands over to the console's own sign-in page. Register opens the server's page in the browser |
| Sessions        | One sign-in per server in the Keychain, handed to the page as `window.substrateShell.session`, which the page reads and never stores; signing out in the console, or a refused token, tells the app, which revokes it and shows the connect screen. One website data store per server keeps the console's own state |
| The page's view | `window.substrateShell` (`{platform, server}`) is set before any script runs            |
| Links           | Anything outside `substrate://` opens in the system browser                             |
| `window.open`   | A provider's OAuth consent opens in the system browser, and its return lands there too  |
| Downloads       | The export lands in Downloads (macOS) or a share sheet (iOS)                            |
| macOS menus     | Change Server (⇧⌘,), Reload (⌘R), zoom (⌘0, ⌘+, ⌘−), Back and Forward (⌘[, ⌘])          |

The console's side is `web/console/src/lib/shell.ts`: the substrate's origin
and host come from the shell when there is one (a pasted record link, a bare
repository label completed at registration), the session is the app's
(`shellSession`, and `signedOut` when it ends), the sign-in and register
pages name the server with a Change link, and Settings has a Server row. In a
browser there is no shell and none of it renders.

The macOS release build is sandboxed (`console/apple/Support/Substrate-macOS.entitlements`:
network client, Downloads) with the hardened runtime. The debug build runs
outside the sandbox, for the driver below.

## Releases and updates

`mise run apps:release` (a pre-release; `apps:release stable` for a stable
one, from a clean tree) releases every app with a UI, on every platform it
has a UI for; `apps:release prerelease chat sync` releases those two alone.
It publishes to `SUBSTRATE_APPLE_RELEASE_URL`: the path-style address of a
folder on an S3 bucket that anyone may read and the key in
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` may write, with its site at
`SUBSTRATE_APPLE_SITE_URL` (below), which every release needs. The
addresses name a deployment, so they come from the environment, never from
this tree. The
variables keep their `APPLE_` names because the owner's environment already
holds them. Every app is named by its [app.json](#an-apps-appjson), and
`.mise/apps.sh` knows none by name; the platforms' halves are
`.mise/apple.sh` and `.mise/apps-android.sh`.

```bash
SUBSTRATE_APPLE_RELEASE_URL=https://s3.example.com/public/projects/substrate/apple \
SUBSTRATE_APPLE_SITE_URL=https://apps.example.com SUBSTRATE_APPLE_TEAM_ID=… \
AWS_ACCESS_KEY_ID=… AWS_SECRET_ACCESS_KEY=… mise run apps:release
```

`apple:release` (the console's), `apple:release:sync`, `apple:release:chat`,
`apple:release:workouts` and `apple:site` are aliases of `apps:release
<channel> <app>` and `apps:site` for one release, and go after the first
joint one.

A release runs in this order
([the plan, §9](../docs/plans/app-kit.md#9-releasing-both-platforms-together)),
and each step holds what it says before the next starts:

1. **One publisher at a time.** The release takes a lease, one object at the
   release folder's root (`.apps-release-lease.json`), created only where
   it is absent (`If-None-Match: *`) and changed only where it still holds
   what was read (`If-Match`), with an expiry and a fencing token that every
   taking raises by one. It reads what every feed lists after taking it,
   renews it every two minutes while it works, and checks it before every
   write: a publisher that finds another's token, or its own lease close to
   expiry, stops. A lease past its expiry is taken over, and its taker reads
   everything again; an expired lease is never renewed, and its holder stops
   at its next write. A bucket compares no token, so the fence is at the
   write itself: every write is conditional, an immutable key created only
   where it is absent and a mutable one (a feed, a site document, the
   versionCodes' record) replaced only where it still holds the version
   this run read under its lease, and every write is bounded in time: the
   time it may take is read after its file is hashed, at the last moment
   before the request, a write left less than ten seconds is never sent,
   and curl gives each one up a minute before the lease expires. A
   publisher that stalls after its last check (a sleeping laptop) and
   writes once its lease was taken over is answered 412 over anything the
   next holder wrote, and the next holder is answered 412 over a late write
   it did not read, and stops rather than lose either. Both stores the
   release writes (the release folder and the site) are refused before
   anything is built if they answer conditional writes as if they were
   plain ones.

   What this does not do is fence at the store: an S3-compatible bucket
   compares no token. Giving a write up stops this side only, so a request
   the bucket already received (from a process stopped mid-upload, or a
   bucket that applies it late) can land after the lease expired, and so
   can one from a machine whose clock is more than the minute behind. Such
   a write is still conditional, so it lands only over the version its run
   read: where the next holder wrote that key since, it is refused and
   nothing is lost; where the next holder has not reached it yet, it lands,
   and the next holder's own write of that key is then refused and its run
   stops, for a rerun to read again. The one late write that lands unseen
   is over a key whose version repeats (the next holder wrote back the
   bytes the late run read), and it puts there what the late run would
   have written under its lease. The comment heading "one publisher at a
   time" in `.mise/apps.sh` says the same.
2. **Everything built and checked first**, from one commit under one
   version, and nothing goes up until all of it passed. Each Apple build's
   Info.plist is held to app.json (bundle id, and the client id and
   redirect under its `clientIDKey` and `redirectKey`) and to the version;
   a Mac build's signature is verified, and every build must be signed with
   its associated domain. A build whose client id or redirect is not an
   https one is refused, so no release signs in through a loopback port. Each Android APK's signature is
   verified and its certificate, package, versionCode, versionName and
   minimum SDK are read back from it (below). The closures are built and
   held to their locks, then checked as the server admits them, and the
   site is built.
3. **Staged.** The build is sealed under `build/apps/releases/<build>/`
   (`staged.json` lists every file's sha256 and what the stage was made
   for: the mode, the release folder, the site, its upload address, the
   authority, the team and the export methods, and the Android certificate
   (`dry-run` for a dry run's throwaway key); the files are made read-only),
   and its files go up under each feed's `releases/<build>/`,
   where no feed names them yet. Those keys are immutable: a key already
   holding the same bytes is passed over, and one holding other bytes stops
   the release.
4. **The site** (below), the closures first and the authority document last.
5. **Each app made current, last and alone**: its `release.json`, naming
   every platform's build, after every file it names; then the feeds its
   installed builds read today, at the addresses they read (`index.json`,
   Sparkle's `appcast.xml`, the install page and the iOS manifest),
   rewritten from the index published now, which is written only over the
   version of it that was read. A release of three apps can stop with one
   current and two not.

**A rerun resumes.** `SUBSTRATE_APPS_RELEASE_BUILD=<build> mise run
apps:release` builds nothing: it checks every staged file against
`staged.json`, refuses a tree whose `HEAD` is not the commit it built and a
run whose release folder, site, authority or signing identities are not
the ones the stage was made for (its builds carry them stamped in), and
carries on where the last run stopped, reading what is published before
each write. Nothing else reuses a staged build, and a release never
resumes a dry run's: it looks for stages where a dry run keeps none, and
refuses one that says it was a dry run's or carries a dry run's update
signature.

**A dry run is every step against `build/apps`.**
`SUBSTRATE_APPS_RELEASE_DRY_RUN=1` builds, stages (under
`build/apps/dry-run/staged/<build>/`, apart from a release's), publishes and
activates into `build/apps/dry-run/release` and `build/apps/dry-run/site`,
simulated buckets with the same conditional writes and time bounds, so the
lease, a rerun and a conflict can be tried there; they persist between dry
runs (`chmod -R u+w build/apps && rm -rf build/apps` starts over). It unsets
the AWS key, the App Store Connect key and the Android release key's
variables (`SUBSTRATE_ANDROID_KEYSTORE`, `_KEYSTORE_PASSWORD`, `_KEY_ALIAS`,
`_KEY_PASSWORD`, `_CERT_SHA256` and `_PREVIOUS_CERT_SHA256`) before anything
else, and signs every Android build with a throwaway key `keytool` makes in
the run's own directory, which goes with it, so the APK is verified and
named in the dry run's `assetlinks.json` with that key's fingerprint; it
never passes
`-allowProvisioningUpdates`, archives every Apple build with signing
switched off (`CODE_SIGNING_ALLOWED=NO`, no identity, no team, no profile)
and takes the app out of the archive in place of an export, which would
sign it, so it reads no keychain, and checks that no build it made names a
signing identity (an app that does not archive unsigned is a placeholder,
and it says so); it writes no closures lock, and the one function that
uploads and the one that signs a request refuse to run in it. Only in a dry
run: `SUBSTRATE_APPS_RELEASE_PLACEHOLDERS=1` stands placeholders in for
every build, `SUBSTRATE_APPS_RELEASE_ANDROID_BUILD=<program>` another
program in for `android:release:build`,
`SUBSTRATE_APPS_RELEASE_STOP_AFTER=stage`, `site` or an app's id stops there
as a failure would, `SUBSTRATE_APPS_RELEASE_SUSPEND_AT=<store>/<key>` stops
the whole run as a sleeping machine would, just before that write reaches
the store (`kill -CONT <pid>` wakes it), `SUBSTRATE_APPS_RELEASE_LEASE_MARGIN`
shortens the minute a write leaves unused before the lease expires,
`SUBSTRATE_APPS_RELEASE_SLOW_HASH=<seconds>:<suffix>` makes the hash of
every file whose path ends in `<suffix>` take that much longer, to try a
write the hash left too little time, and
`SUBSTRATE_APPLE_SITE_PUBLISHED=<file>` tries the site's merge against a
saved document.

Each invocation works in its own directory under `build/apps/runs/`,
removed when it exits, so two in one checkout share no working file. What
they do share is held by local locks under `build/apps/locks/`: a build's
stage, which one invocation stages or resumes at a time, and this
checkout's builds (the Xcode project and derived data, the Gradle outputs),
which one invocation runs at a time. Each lock is an `flock` its holder's
process keeps, which the system drops when the process ends, so no run
removes another's lock and a killed one leaves none.

**An app's client id names it on every server.** Substrate Sync and
Substrate Chat each publish a client ID metadata document, `client.json`,
and a release stamps its URL into the build as the app's OAuth client id.
That URL's host is what the owner is shown at the head of the approval
page, and the server names the app's actor from what the approval proved
(decision 0209): `app:<authority>` for an app its authority's document
lists (`app:substrate.reamde.dev` for these apps in a release),
`app:local` for a build whose access went to a loopback address, and
`app:<host>` of the client id for one nobody verified. Two apps under one
authority, or unverified on one host, share that actor. The host must
therefore be one only the publisher serves: the documents go on the site,
at `/apps/<app>/client.json`, and a release refuses a shared endpoint there
before it builds anything (path-style S3 such as
`s3.<region>.amazonaws.com`, `storage.googleapis.com`, a raw file host),
since anybody could publish a document there that the approval page would
head with the same name.

**A site gives every app a claimed callback, and every release needs one.**
`SUBSTRATE_APPLE_SITE_URL` is an https origin on a host of the publisher's
own, served at its root (Apple reads the association file from the host's
root and nowhere else, as Android reads `assetlinks.json`), and a release
without it is refused before it reads or builds anything: a released app
signs in only through the https callback it claims there, never through a
loopback port, where any program on the device could take the code.
`mise run apps:site` publishes, under the release lease, and every release
publishes again:

- `/.well-known/apple-app-site-association`, naming each app id
  (`SUBSTRATE_APPLE_TEAM_ID` and the bundle id) under `webcredentials` and
  under `applinks` for its own `/apps/<app>/callback`;
- `/.well-known/substrate/authority.json`, the authority
  (`SUBSTRATE_APPLE_SITE_AUTHORITY`, else the site's host), every app by its
  client id with the packages it asks for, and under `packages` every
  published version of every package an app's app.json `publishes`
  (Workouts' `training` and `trainingcoach`, Tasks' `tasks`) with its
  closure's URL and sha256, newest first;
- `/packages/<package>-<version>.yaml`, each closure: the multi-document
  YAML of the app's `package/`, built by `.mise/closures.py` (the file
  declaring the package, then the file declaring each entry of its bundle's
  `installs`, in order) and held to the app's `package/closures.lock.json`;
- `/.well-known/assetlinks.json`, naming each Android app's package and the
  SHA-256 of the certificate its APK is signed with, read from the signed
  APK this release staged, else from the newest Android build its feed
  lists, every Android app's feed read again under the lease whether this
  release ships it or not (and `SUBSTRATE_ANDROID_PREVIOUS_CERT_SHA256`
  during a rotation), for its links and its credentials;
- `/apps/<app>/client.json` for every app with a UI, whose redirects are
  each platform's callback, `https://<site host>/apps/<app>/callback` for
  Apple's and `/apps/<app>/android/callback` for Android's, and which names
  the authority as `substrate_authority`.

A published version never changes: the task reads the live document first,
after taking the lease, from the store it is written to and with the
release's key (absent is a first publish; a cache in front of the site
could serve an older one, and a bucket that forbids listing answers an
anonymous read of a missing key with 403), keeps its version and replaces
it only over that version, carries every package it lists forward whole, its versions joined with this tree's,
and refuses to publish a listed version whose closure this tree builds
with another digest, or a version below the newest listed that was never
published. Every closure it publishes for the first time is checked as the
server admits it before anything goes up: `substratectl publish --check`,
built from the tree, parses it like the server's catalog against the live
document and its newest published closure, and refuses a narrowing unless
`SUBSTRATE_APPLE_SITE_ALLOW_NARROWING=1`. The closures go up first and the
document last, so the document never names a closure that is not there yet,
and a release publishes the site before it makes any build current. After
a publish each app's `package/closures.lock.json` is written with what is
published, to be committed. `SUBSTRATE_APPS_RELEASE_DRY_RUN=1` builds the
site in its run's directory and publishes it into `build/apps/dry-run/site`
alone (`SUBSTRATE_APPLE_SITE_DRY_RUN=1` still asks `apple:site` for the
same).

The files are PUT to `SUBSTRATE_APPLE_SITE_UPLOAD_URL` when that is not the
site itself (a bucket behind the host), with the release's key. The site
then is each app's client id, and a release stamps the app's redirect
(`SUBSTRATE_<APP>_REDIRECT`), the site host (`SUBSTRATE_SITE_HOST`) and
`SUBSTRATE_ASSOCIATED_DOMAINS=YES`, which signs the app with its `-site`
entitlements in its `apple/Support/`: `webcredentials:` and `applinks:` on the site
host. The provisioning profile must carry the Associated Domains
capability. A local build sets none of these, carries no associated domain
and signs in through a loopback port, as its loopback client id says. The
kit holds the other half: a build whose client id is an https one and
whose claimed redirect is missing or not an https URL refuses to sign in
(`UnclaimedRedirect`) rather than fall back to a loopback port. The task prints the record the
authority's DNS needs once:
`_substrate.<authority>. TXT "v=substrate1 doc=<site>/.well-known/substrate/authority.json"`.
The release builds stay in the release folder.

The version is the next patch after the last released one, plus the build
number and the commit, `0.113.1-pre.20261021.153012+ac85863e` (`.dirty`
when the tree was); the build number is the UTC time, so it only rises, and
it is what one release is compared to another by. The folder holds:

| Path                | What                                                                    |
| ------------------- | ----------------------------------------------------------------------- |
| `index.json`        | Every release, newest first; what the iOS app reads                     |
| `appcast.xml`       | Sparkle's feed; pre-releases ride its `prerelease` channel              |
| `index.html`        | The install page: an iPhone installs from it in Safari, a Mac downloads |
| `releases/<build>/` | The macOS zip, the IPA, its install manifest and icons, `release.json`  |

A released build carries the folder's address; a local build carries none
and never looks. On macOS, Sparkle checks at every launch, every four hours
after and on Substrate → Check for Updates, verifies the archive against the
EdDSA key made on the first release (kept in the login keychain under
`substrate`; losing it means every installed Mac app is replaced by hand once)
and installs it. On iOS only the system may install an app: the app reads
`index.json` at launch and when it comes to the foreground, at most hourly,
and offers the newer release's install link. Both include pre-releases when
the running build is one; the Mac's app menu turns that off. On both, the
console's Settings → Signed in shows the app's version with a Check for
updates button, which asks the shell (`checkForUpdates` in
`web/console/src/lib/shell.ts`) to check now.

Provisioning goes through the Apple ID signed in to Xcode, a session that
expires and can only be renewed in Xcode's window. An App Store Connect API
key replaces it for a shell: set `SUBSTRATE_APPLE_ASC_KEY_PATH` (the
`AuthKey_….p8`), `SUBSTRATE_APPLE_ASC_KEY_ID` and
`SUBSTRATE_APPLE_ASC_ISSUER_ID`, and every build and export passes them to
`xcodebuild`. The key needs the Admin role, because registering an app id's
capabilities (Substrate Sync's HealthKit) is an admin's act. Like the release
address, it lives in the environment and never in the tree.

### Android: the versionCode and the release key

An Android build's `versionCode` is allocated under the lease: the minutes
from 2026-01-01 UTC to the build number's UTC time, the highest code the
app's feed lists plus one, or the highest code ever given to one of its
builds plus one, whichever is largest, so it rises with the build across
machines and stays above anything published or given out when a clock is
behind or a build never finished. Every code given is recorded in the
release folder's `.apps-release-version-codes.json` (by app and build,
written only over the version read, before anything is built), and in the
staged `release.json`; only a rerun of that staged build uses it again, and
the rerun checks the record still gives it to that build. The APK comes
from one task, `mise run android:release:build <app>`, which builds the
app's `apps/<app>/android` module with the release's stamp as Gradle
properties (`substrate.release.version`, `.versionCode`, `.channel`,
`.commit`, `.updatesURL`, `.clientID`, `.redirect`, `.siteHost`), then
aligns it and signs it with the release key, which Gradle never sees: it
runs with the key's variables removed from its environment, and they reach
`apksigner` alone. A release calls the task's program directly, with the
task's tools on its `PATH` and an environment made of the stamp, the key,
the SDK and little else, never through `mise run`, which would load this
machine's mise configuration (a `.mise.local.toml` and the env files it
names, the bucket's key among them) into Gradle and its daemon.

The key is made once, by the owner, outside the tree, and kept as a secret
with its passwords (a password manager, and a backup of the file):

```bash
keytool -genkeypair -keystore ~/secrets/substrate-android-release.jks -alias substrate \
  -keyalg RSA -keysize 4096 -validity 36500 -dname "CN=Substrate"
keytool -list -v -keystore ~/secrets/substrate-android-release.jks -alias substrate | grep SHA256:
```

A release reads it from the environment: `SUBSTRATE_ANDROID_KEYSTORE` (the
file), `SUBSTRATE_ANDROID_KEYSTORE_PASSWORD`, `SUBSTRATE_ANDROID_KEY_ALIAS`
and `SUBSTRATE_ANDROID_KEY_PASSWORD`, which reach `apksigner` through the
environment rather than its command line, and `SUBSTRATE_ANDROID_CERT_SHA256`,
the fingerprint the second command prints. A release refuses an APK signed
with any other certificate, so a debug key never ships, and `assetlinks.json`
names the certificate read from the signed APK itself. A dry run reads none
of these: it unsets them and signs with a throwaway key of its own (above). Android installs an
update only when it is signed with the same key: losing the key means every
install is replaced by hand, as losing Sparkle's does on the Mac.

Rotating it is APK Signature Scheme v3's lineage: make it with
`apksigner rotate --out lineage --old-signer --ks <old> --new-signer --ks <new>`,
sign with the new key and the lineage (`android:release:build` signs with one
key today, so the rotation adds `--lineage` there), set
`SUBSTRATE_ANDROID_CERT_SHA256` to the new fingerprint, and set
`SUBSTRATE_ANDROID_PREVIOUS_CERT_SHA256` to the old one, so
`assetlinks.json` names both until no install signed with the old key alone
remains.

### Signing the Apple builds

Both are signed with the team's Apple Development identity, so the IPA
installs on the devices in the team's development profile (with Developer
Mode on) and the Mac app opens after Privacy & Security → Open Anyway once.
`SUBSTRATE_APPLE_EXPORT_IOS=release-testing` and
`SUBSTRATE_APPLE_EXPORT_MACOS=developer-id` switch to ad hoc and Developer ID
signing once those certificates exist.

## Driving a debug build

A debug build carries `DebugDriver`: it watches `automation/` in the app's
temporary directory, runs an `eval.js` found there in the page as an async
function body and writes the answer to `result.json`, and answers a `snap`
file with `snap.png`, the web view's snapshot. `SUBSTRATE_SHELL_SERVER` in
the environment starts it pointed at a server, which still asks for a
sign-in.

```bash
# macOS
SUBSTRATE_SHELL_SERVER=http://localhost:8080 \
  apps/xcode/build/dd/Build/Products/Debug/Substrate.app/Contents/MacOS/Substrate &
dir="$(getconf DARWIN_USER_TEMP_DIR)automation"
echo 'return document.title' >"$dir/eval.js"; sleep 1; cat "$dir/result.json"

# a simulator: the app's data container
SUBSTRATE_SHELL_SERVER=http://localhost:8080 mise run apple:sim
dir="$(xcrun simctl get_app_container booted dev.reamde.substrate.console data)/tmp/automation"
```

Release builds carry none of it.

## Substrate Sync

A second app in the same project: `SubstrateSync` (bundle id
`dev.reamde.substrate.sync`), iPhone and iPad only, iOS 26. It carries no
console and no Sparkle. It reads the device's Health, Contacts, Calendar,
Reminders and the places it stays at, and pushes them into one repository,
over the API alone, with access of its own the owner approved, or with the
owner's password on a server too old to give it that. Nothing is written
back to the device. Its share extension, Send to Substrate, saves what any
app shares. Both are built on [SubstrateKit](kit/README.md): the
address, discovery, the requests and their errors, the sign-in, the session
in the Keychain and the status check are the kit's.

```bash
mise run apple:build:sync     # the app for the simulator
mise run apps:release prerelease sync   # archived, signed and published under sync/
```

| Source    | Lands as | How |
| --------- | -------- | --- |
| Contacts  | `providers.substrate.reamde.dev/apple/addressbook` and `…/contact` | `PUT` per changed contact, `PATCH` to null for a vanished key, `DELETE` for a vanished contact, then the address book row |
| Calendars | `…/apple/eventstore`, `…/calendar` and `…/event` | every event calendar and every occurrence from 90 days back to 180 ahead; an event that ages out of the window keeps its row |
| Reminders | `…/apple/reminderlist` and `…/reminder`, under the event store | every list and every reminder, completed ones too; a deleted one is removed |
| Places    | `…/apple/visitstore` and `…/visit` | the visits iOS reported while Places was on, kept a year on the phone, named by Apple Maps |
| Health    | `providers.substrate.reamde.dev/applehealth` mirror rows, then observations, sleep and workouts through the provider's own adapter, under `substrate.reamde.dev` | Health Auto Export's JSON to `/webhooks/<authority>/applehealth-webhook`, two deliveries per local day |
| Shares    | `…/apple/share`, the images as blobs | the share extension, once per share |

The ids and the field rules are the apple package's
[README](../kinds/providers.substrate.reamde.dev/apple/README.md); the
Health format is the one `internal/synth/applehealth.go` emits, and two
goldens hold the app to it from both sides:
`internal/providertest/testdata/applehealth/app_minutes.json` and
`app_seconds.json`. The app's tests compare its encoder with them byte for
byte, and `internal/providertest/substratesync_test.go` runs them through
the provider and the adapter. After a deliberate change to the format,
regenerate them and run both:

```bash
TEST_RUNNER_SUBSTRATE_UPDATE_GOLDEN=1 xcodebuild -project apps/xcode/Substrate.xcodeproj \
  -scheme SubstrateSync -destination 'platform=iOS Simulator,name=iPhone 18 Pro' test
go test -count=1 -run TestSubstrateSync ./internal/providertest/
```

**Signing in** reads the address's discovery document and its OAuth
metadata, and takes one of two doors, which make two kinds of session
(`SyncManifest` in `App/Manifest.swift`).

- A server whose metadata lists the `package`, `account` and `webhook`
  detail types, and that is 0.114.0 or later where it names a release, gets
  the app authorization flow, as Substrate Chat does: the browser sheet on
  the server's own sign-in and approval page, which asks for
  `write:providers.substrate.reamde.dev/apple/*`, and for every write the
  applehealth package's own functions and triggers reach (a package an
  approval installs reaches no further than the approved scopes): the
  account and the deliveries by name, `write:…/applehealth/*`, health sleep
  and workouts and `write:substrate.reamde.dev/observations/*`; and sets up
  on approval what Set Up would: `providers.substrate.reamde.dev/apple` at
  version 3 or later, `…/applehealth` at 5 or later, the Health account
  `substrate-sync-<first 8 characters of the install id>` (named for the
  device, in its time zone) and the `applehealth-webhook` trigger, whose
  `webhook:` scope the token then carries. The client id is the
  `SubstrateSyncClientID` Info.plist key (`SUBSTRATE_SYNC_CLIENT_ID`), and
  a local build's loopback `http://127.0.0.1/substrate-sync`; a release
  claims the redirect in `SubstrateSyncRedirect`
  (`SUBSTRATE_SYNC_REDIRECT`). The sign-in
  screen lists what the approval will ask for, in the approval page's
  words, before it opens the sheet.
- Any other server gets the password form, as before: the repository, the
  password, and a code only when `registration.totpRequired` says so.

Either session is kept in the Keychain under the service
`dev.reamde.substrate.sync` and the app's access group, which the share
extension reads too; a session an earlier build kept still reads as a
password one. Sign Out forgets it on the phone at once and revokes the token
in the background (the kit's `Session.revoke`: an app token at `/oauth/revoke`
under the client id it was approved for, a password one with its own
`DELETE /tokens/{id}`), so it works with the server unreachable or the token
already refused. The token is kept in the Keychain until the server answers
200 (a busy server's 429 or 503 is no revocation; a redirect is never
followed), tried again at each launch, and Home, Settings and the sign-in
screen say so while it still works, once for each server and repository.
Where the Keychain will not keep it, Sign Out revokes it first and forgets
the session only once the server confirms; a token neither kept nor revoked
stays signed in, and the app says why, so no token is ever dropped. What the
phone remembers is bound to the repository it was pushed to: signing in to
another one, or finding the contacts' address book, the calendar store or the
Health account gone from the server, sends everything again.

**An app session asks whether it is still set up.** At launch and on return
to the foreground, at most every five minutes, and at once when a sync meets
something only an approval clears, the app runs the kit's status check
(discovery, the metadata, `POST /api/v1/authorizations/check` with its whole
request, and when the access ends). Home stays reachable: a package behind
the version the app writes, the Health account or the webhook gone puts the
kit's status in Set Up's place, listing each change in the approval page's
words, with Review and Approve, which opens the review and then the flow
again with the whole request. Scopes the app lacks, access ending soon or a
server it could not reach show as a banner on Home, and so does a change the
approval page would refuse (a blocked row: a quarantined package, one
declared by hand, an account deleted): the server's own sentence says why,
and its button opens the console page the server names to fix it, or the
review where it names none, since the page shows why with Approve off. A
package only a newer server ships waits for that update, with no button. A
scope the owner left unticked is never asked about again; Settings → Change
Access offers it back under "You left these out last time". A source whose
scope the owner left unticked stops with that scope
named, before it reads anything: a scoped read of a kind the token does not
reach answers 404, which would otherwise read as rows the server lost. A
Health account deleted on the server says so; the approval leaves a deleted
row alone, so there is nothing to approve until the server lets it go. After
a review the new session is kept and the old token revoked. Settings shows what was approved
and until when, with Change Access and Sign Out, and Server Status, what the
approval set up. A token the server refuses (the access ended, or was revoked
in Settings, under Apps) stops every sync and shows the kit's access ended
screen, whose Sign In Again runs the flow on the same server. A 403 with
`insufficient_scope` is "needs your approval", never "sign in again".

**A password session** works as it always has: Set Up below, the trigger's
key, the account made when it is missing. A refused token stops every sync
and shows one screen whose button signs in again. When its server can now
give the app access of its own, Home offers Move to App Access: the flow with
the same install id, so the approval finds the account and the webhook in
place, the new session kept, then the password token revoked with its own
`DELETE /tokens/{id}`, carrying itself (`/oauth/revoke` under the app's
client id would answer 200 and revoke nothing). The replaced token is kept in
the Keychain before the new session is saved over it, revoked before the
status check runs, and tried again at each launch until the server answers;
Home says so while it still works.

**Set up**, for a password session, lists what the repository lacks and
does it with one button:
installs (or upgrades to version 3) `providers.substrate.reamde.dev/apple`
and installs (or upgrades to version 5) `…/applehealth`, which ships the
adapter and installs the `substrate.reamde.dev/health` catalogue it
requires; then it creates the Health account
`substrate-sync-<first 8 characters of the install id>`, and turns on the
`applehealth-webhook` trigger. It keeps a key already on the trigger unless
the owner says to replace it, and otherwise sets a new 32-character one. A
refusal is shown in the server's own words.

**Health deliveries carry the session's credential.** Under an app session
the token is the credential (`Authorization: Bearer`, holding
`webhook:applehealth-webhook`): the trigger, which the token cannot read, is
never read, no key ever reaches the phone, and revoking the app ends its
deliveries. The account is never written: one gone from the server stops
Health with a review to approve, and every day is sent again once it is
back. Under a password session every Health run reads the trigger's key and
sends it, and makes a missing account. Either reads the trigger's parked
deliveries to tell a refused day from one still filing.

**Health** goes as two deliveries per local day, oldest day first: every
metric at one row per minute (`automation-aggregation: minutes`), and the
sleep segments and workouts (`seconds`). The first sync sends the history
Health → History names (14 days unless it says 30 days, 3 or 6
months, a year, or everything the phone holds); each later one sends the last
three days again and any day not yet accepted. A day counts as sent only once
the server has filed it (its `applehealth/export/<fire id>` receipt); one the
server parked stays queued and is sent again. Days go one after another
while the server files behind them, at most fourteen days ahead of its
filing: waiting for each batch stood the progress still long enough for iOS
to end a continued sync, and never waiting filled the server's spool. A
range longer than a month first asks HealthKit which days hold data, so years
of history are not read one empty day at a time. That answer is kept in
`health-scan.json` (`HealthScan` in `Coverage.swift`), which Home, Coverage
and a sync share: the first scan reads the history 90 days at a time, saving
after each and saying how far it has got, and every later one reads only the
last week and any stretch further back than it has read. A day the sync finds
empty is dropped from it, and Coverage's Read the Whole History Again starts
it over, for data an app wrote into days already read. Health access is
asked again, before a sync the owner starts, whenever the build reads a type
the phone was never asked about; until it is allowed, such a type reads as
nothing, as a refused one does, rather than failing every day. A day read in
part is sent, waited for like any other, and queued to be sent whole, so the
phone never runs ahead of the server's filing, whose spool answers 503 when
it is full; a delivery waits out a 503 for up to four minutes. A background run sends only
the last three days. A delivery replaces a metric's rows across its span, so
a day is always sent whole, and a day larger than 4 MiB is split by metric.
Besides the measured metrics, a day carries what is logged: mindful minutes
(each session at the minute it starts), water and eleven nutrients, and basal
body temperature, which the adapter maps to the `health/*` metrics of those
names; cycle tracking, as the `cycleTracking` section (`cycleevent` rows); and
each workout's GPS route, thinned to 15,000 points, which stays on the
workout's mirror row.

**Reminders** are read whole each sync: every list (an `EKCalendar` for
reminders) and every reminder, with its due day, and its due moment where it
has a time. A list or a reminder gone from the phone is deleted, and an empty
answer from EventKit deletes nothing.

**Places** is off until it is turned on, because it asks for Always location
access. It uses iOS's visit monitoring, which reports a stay when the phone
arrives and again when it leaves, at little cost to the battery, and relaunches
the app in the background to do it. Each report is kept in a log on the phone
for a year; a sync names up to 25 new visits a run through MapKit's reverse
geocoder and sends them all, so a reset repository gets the year back. iOS
keeps no history of its own, so Places starts when it is turned on.

**Send to Substrate** is a share extension: a link, text and up to four
images from any app's share sheet, with a note, saved as one `share` record.
It reads the app's sign-in from the Keychain group the two share, either
kind, uploads the images as blobs (an app token may, since it writes
`apple/share`, whose `images` are a `blobref`) and writes the record within
the minute the server keeps an
unreferenced blob, writing it again part way through when a slow uplink would
outlast that minute. A link shared again updates its record; a share without
one keeps one id per sheet, so a Save tried again updates the first try.
Cancel stops a save under way, and deletes what it wrote of a share without a
link.

**Errors and waiting.** Every request has a time limit sized to its work:
discovery and sign-in 20 seconds, a read 30, a Health delivery or an image
two minutes, an install five. An install is never sent twice, and one that
outlasts its limit says so ("taking long") rather than "failed", because the
server goes on; the check after it finds the install done. Set Up's and Check
Again's spinners end with the work, never after the error. A batch of writes
that all fail for the network stops the run at the first batch, and a
refused token stops it at the first refusal; a refused Health webhook key
asks for Set Up, and a refused app delivery for a review, and neither signs
the owner out. A read that fails (Reminders,
the events of a calendar that held some, a Health day) deletes nothing and
marks nothing sent. Errors are said in sentences that name the server and
what to do, with the server's own words where it gave some.
`sync/apple/UITests/SetupTimeoutTests.swift` holds the Set Up case against
`xcode/scripts/slowserver.py`, a proxy that holds each install longer than the app
waits:

```bash
python3 apps/xcode/scripts/slowserver.py http://localhost:8080 8 8093 &
TEST_RUNNER_SYNC_SLOW_SERVER=http://localhost:8093 TEST_RUNNER_SYNC_E2E_REPOSITORY=<fresh> \
  TEST_RUNNER_SYNC_E2E_PASSWORD=… xcodebuild -project apps/xcode/Substrate.xcodeproj -scheme SubstrateSync \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro' test -only-testing:SubstrateSyncUITests/SetupTimeoutTests
```

The UI tests launch a debug build with `SUBSTRATE_SYNC_PASSWORD_DOOR=1`,
which takes the password door on any server, since a test cannot approve
in the browser sheet. The unit tests hold the rest: the request (scopes and
details), a password session kept by an earlier build, and which credential
a delivery carries under each kind. With `TEST_RUNNER_SYNC_SNAPSHOTS` naming
a directory, they also draw the status screen, needing approval and up to
date, and the review, to PNG files there.

**Home is an overview.** A status card says what is syncing (the source,
its step and how far it has got, and Stop) or how the last sync ended, above
Sync Now. Each source is one row: what it has synced of what the phone holds,
when, and its state as a badge (Up to date, Syncing, Queued, Behind,
Processing, Stopped, Failed, No access, Off). A stop is not a failure. Health
is Behind, never Up to date, while days with data inside its history were
never delivered, whatever its last run said, and the card says how many. A source that is running or waiting its turn shows
that, never the error of the run it is replacing. Tapping a source opens its
page: the state with the last run or its error and a button that syncs that
source alone, its coverage once (Health: the days with data inside the
history, those waiting for the server, those going at the next sync, a chart
grouped to fit the history, and every period a tap away; the days older than
the history are counted apart and sent on request), its settings (the
switch, access, Health's history, which calendars), and its last runs.
Activity is one timeline: each run with how it ended and how long it took,
its log lines folded inside it, filterable by source. The account, the
background frequency, the server set up, the version and Sign Out are behind
the gear.

**Calendars** sends the calendars turned on in Calendars → Calendars, by
account. The setting keeps the ones turned off, so a calendar added on the
phone later is sent until it is turned off; a calendar turned off is removed
from the repository, with its events, at the next sync, as one deleted on the
phone is.

**A day waiting for the server** keeps the fire ids of its deliveries, and
the next sync reads their receipts before it sends anything, so a day the
server filed since is not sent again.

**In the background** a refresh task syncs when the system allows, and
HealthKit's observer queries (heart rate, steps, sleep, workouts) wake the
app to send Health. Settings → Sync in the background picks hourly, every
six hours, daily, or only on Sync Now: it is the soonest a background run
may sync a source again, the refresh task's earliest start, and HealthKit's
delivery frequency (none when syncing by hand). iOS decides the moment.

**A large sync runs on when the app leaves the screen.** When the owner starts a
sync with more than a week of Health days to send, more than 500 rows of any
other source, or a first sync of a source the phone has not counted, the app
asks iOS for a continued processing task (`ContinuedSync` in
`Background.swift`, iOS 26's `BGContinuedProcessingTask`). iOS keeps the app
running and draws the progress itself as a Live Activity on the Lock Screen
and in the Dynamic Island: the status card's headline, the running step or
Health's month ("March 2019 · 12 of 31"). Its stop button stops the sync as
Stop does. iOS ends a task as stalled (its log says `Task has not reported
progress within expected cadence`) unless the bar climbs past its highest
point within about thirty seconds, and counts nothing after a bar that
reached the whole. So the system's bar only ever rises and never reaches the
whole before the end: the quick steps before a run (receipts of earlier days,
the scan) fill only its first two percent, and Health then counts its whole
run, each day half read and sent and half filed, while the app's own screens
show the month. A debug build carries `ContinuedProbe`, which tries iOS's
rules apart from any sync: `SUBSTRATE_SYNC_PROBE` in the launch environment
(`xcrun devicectl device process launch --environment-variables`) runs a
probe that counts to a hundred (`apple`, `main`, `reset`, `fine`, `burst`,
`retitle`, `full`, `dip`), or a real Sync Now (`sync`), and logs what iOS did
with it to Activity. A stop by iOS is logged in Activity with the step
and how long the bar had stood. Health is encrypted while the phone is
locked, so a lock stops the Health part of a sync, says so, and sends nothing
it could not read. The app
ships no widget extension, and a small sync asks for nothing. Where iOS will
not run one now, the sync runs as before, while the app is on screen. The debug build's Home has Add Sample
Data, which writes yesterday's Health samples, three contacts and a sample
calendar for a simulator to sync.

**Releases** go to `$SUBSTRATE_APPLE_RELEASE_URL/sync/`, a folder of their
own with the same `index.json`, install page and manifests (`feed.swift`
reads the app's `name` from `release.json`), and the app's Check for Updates
reads it. The build needs HealthKit on the development profile: with
automatic signing `-allowProvisioningUpdates` adds it to
`dev.reamde.substrate.sync`, else enable it on the identifier in the
developer portal. The IPA installs on the team's registered devices, with
Developer Mode on.

## Substrate Chat

A third app in the same project: `SubstrateChat` (bundle id
`dev.reamde.substrate.chat`), one SwiftUI target for iPhone, iPad and Mac,
iOS and macOS 26. It is the console's agent chat as a native app: it carries
no console, speaks only the API, and keeps a repository's chats on the device
so every screen draws before it asks the server anything. The design, the
feature list and what the reviews of it changed are in
[chat/DESIGN.md](chat/DESIGN.md). Everything below its views is `ChatKit`
(`chat/ChatKit`), a Swift package over the kit's portable libraries that
builds and tests on Linux too (`mise run apps:test:linux`): the chat list as
the app's root under the kit's `LinkController`, each conversation a child of
it, and DESIGN.md's seven rules as the runtime's behaviour, each with a test
by its number. The app draws its presentations and sends its commands.

```bash
mise run apple:build:chat     # the Mac app and the iOS simulator app
mise run apple:sim:chat       # the iOS app on a booted (or the first) iPhone simulator
mise run apple:test:chat      # ChatKit's tests, then the app target's, on the Mac
mise run apps:release prerelease chat   # both platforms, signed and published under chat/
```

**The chat is the console's.** The transcript is the `llm/message` rows folded
the way `web/console/src/lib/api/transcript.ts` folds them, a reply streams as
an overlay over them, and the overlay is dropped in the same update the rows
land in once the turn settles, so nothing blinks. A chat that is running when
it is opened is attached to (`…/llm/thread/{id}/events`), a dropped stream is
attached again with backoff, Stop posts `…/stop`, and a send the server
refused, or whose delivery is unknown, says so with the message to copy and
is never sent again on its own.

**Signing in** is the substrate's app authorization, through
[SubstrateKit](kit/README.md) under Chat's manifest
(`ChatManifest` in `chat/ChatKit/Sources/ChatKit/ChatManifest.swift`): the kit's connect screen checks
the address's discovery document and OAuth metadata, and the system's
sign-in sheet opens the server's own sign-in and approval page, where the
owner chooses what the app may do (talk to the agents, `agents:*`; apply
what they suggest, `decide:*`; read the provider rows; read the records a
chat links to, `read:*`) and for how long. The redirect comes back to the
app's claimed https callback in a release, and to a loopback port the
app listens on (RFC 8252) in a local build, and the code is
exchanged with
its PKCE verifier; the app never sees the password, and its writes are
recorded as `app:substrate.reamde.dev` in a release the site's authority
document lists, `app:local` in a loopback build, and `app:<host>` of its
client id in one nobody verified. A release publishes the app's client ID metadata
document as `chat/client.json` (see
[Releases and updates](#releases-and-updates) for the host it goes on) and
stamps that URL into the build (`SubstrateChatClientID`); any other build
signs in as the local app
`http://127.0.0.1/substrate-chat`. A server whose metadata answers 404 gets
the password form; one whose metadata does not list `agents:` and `decide:`
(between decisions 0194 and 0195) would refuse the request with an error
page, so it gets the kit's too-old screen instead, as does a release older
than 0.114.0, the first to carry both. A build between releases (`dev`, or
`v0.113.0-143-g…`) is judged by its metadata alone.

The session, either kind, is the kit's, kept where every build kept it (the
Keychain service `dev.reamde.substrate.chat`), and a session an earlier
build wrote still reads. At launch and on return to the foreground, at most
every five minutes, the kit's status check runs for an app session, and the
chat list shows its banner for access ending soon or ended, a server too
old, and a scope a newer build asks for, with Review, which opens the flow
again. A scope the owner left out at the last approval is never asked about
again: it is theirs to add with Settings → Change Access, whose review
offers it back, and which runs the flow and keeps the old access until the
new one is kept. A 403 says to allow it there, never to sign in again. Chat's
requests and their errors are the kit's `SubstrateClient`; it adds only the
agent streams, read through the transport's line stream, and the change feed
is the kit's `WatchFollower`. Sign Out revokes an app token under the
client id it was approved for (none, for a session an earlier build kept
without one), and a password one with its own `DELETE /tokens/{id}`; a
revocation the server does not confirm is kept, tried again at launch, and
said on the sign-in screen and in Settings with the server it is on. A token
the Keychain will not keep is revoked before the session is forgotten or
replaced, and one neither kept nor revoked stays in use, with the reason.

**Instant.** Agents, providers, the chat list and each chat's rows are kept in
Application Support, one folder per server and repository (excluded from
backups; on iOS protected until the first unlock), and drawn at launch. The
eight most recent chats whose rows are out of date are read in the background.
Cached rows are current while their thread is settled and its `version` is the
one they were read under. The change feed (`/api/v1/changes?watch=1`), resumed
from the list read's `head` and `generation`, keeps the list and the open chat
live while the app is in front (and while the Mac app runs). Sign Out deletes
the folder and revokes the token in the background.

**Assistants.** Settings → Assistants lists every agent with a switch that
offers it for new chats and to the Action Button, the default for new chats,
and an Add Key for an agent whose provider has none: the console's provider
record for an app token, which never writes a key, or the provider row's
`apiKey` for a password sign-in (never kept). The agents whose purpose is primary are
offered until the owner says otherwise; one hidden from chat is listed apart.

**Voice typing.** The microphone runs `SpeechAnalyzer` with a
`SpeechTranscriber` (on device; a `DictationTranscriber` where that is not
available), the speech model downloaded the first time a language is used.
The words heard so far are drawn in the composer, the guess dimmed, and land
in the field when listening stops; Send stops, finalizes and sends.

**Notifications.** The server has no push channel, so the app notifies what it
sees: a reply that settles in a chat not on screen, and a new question or
suggestion waiting on the owner, each once. On iOS a turn still streaming when
the app leaves is kept running as a continued processing task, which iOS draws
with a Stop button, and a refresh task checks now and then when iOS lets it.

**The Action Button.** Two App Shortcuts: New Chat (an assistant, else the
default; optionally listening) and Talk to an Assistant (listening from the
start). Either is a choice for the Action Button under Settings → Action
Button → Shortcut.

**Releases** go to `$SUBSTRATE_APPLE_RELEASE_URL/chat/`, a folder of their
own with the same feeds and install page as the console app's; the Mac build
updates itself through Sparkle with the console app's key, and the iOS build
offers each newer release.

## A new app

`mise run apps:new <id>` makes `apps/<id>/` from `template/`, and every app
after Tasks starts there. The id is one lowercase word: the app's folder,
its feed, its bundle id's last label (`dev.reamde.substrate.<id>`) and its
package's name (`substrate.reamde.dev/<id>`). It writes:

| Where | What |
| --- | --- |
| `app.json` | the app named once, asking for its own package at version 1 under `write:` on its kinds |
| `<Id>Kit/` | its core, a Swift package named for the app: `<Id>Core` with one controller, `<Id>App` (its records the kit's `LinkedRecords` over its kinds), its manifest, presenter and fixtures, and a test holding the manifest to `app.json` |
| `apple/` | `targets.yml` (the app, its `Substrate<Id>UI` framework and the tests that draw its views, with its package), the app's scene, the kit's `AppShell` over its root and one screen, Info.plists and entitlements as every app's, and a loopback client id for a local build |
| `package/` | `substrate.reamde.dev/<id>` with one example kind, `item`, and its README |
| `README.md` | the app's README |

and includes `<id>/apple/targets.yml` in `xcode/project.yml`, so
`mise run apple:project` shows the new scheme, `Substrate<Id>`. What it
writes passes `lint:apps` and the server's first-party reach test
unchanged, because the template is a whole app named `template` that both
hold as they hold every other; `apps.sh` and `.mise/closures.py` skip it by
name, so it is never released or published. `xcode/project.yml` includes
the template's own targets, so the project shows its scheme,
`SubstrateTemplate`, beside every app's, and `mise run apple:test:template` runs TemplateKit's tests
and draws its views on the Mac. `apps:new` refuses a result that still
names the template anywhere but a kind's `displayTemplate`.
`mise run apps:new:check` runs `apps:new example` into a scratch copy of
`apps/`: the result's core built and tested in the swift container, which
CI's `apps linux` job runs, and on a Mac the result's project generated, its
app built and its views drawn, which CI (Linux) cannot, so an author
changing the template runs it, with `apple:test:template`, before the pull
request. A change to the template is a change to every app made from then
on; an app already made keeps what it copied.

## Android

The kit runs on Android under a Kotlin UI through one fixed bridge, built by
the Gradle root in `gradle/` with the open-source Swift 6.4.2 and the Swift
SDK for Android, which the `android:*` tasks pin as their own tools (the
`apple:*` tasks keep Xcode's). `mise run android:sdk` installs the
toolchain once, `android:build`, `android:test` and `android:smoke` build,
test and run it on an emulator, and the CI job `android build` builds it on
Linux. [kit/android/README.md](kit/android/README.md) says how the bridge
runs, how its Kotlin is generated, how an app adds its roots, and how
kit-ui draws the shared screens. `mise run apps:gallery` draws every shared
screen's fixtures with SwiftUI and with Compose into `build/gallery/apple`
and `build/gallery/android`, and `build/gallery/index.html` shows each
fixture's two side by side.

## Formatting

`mise run fmt` formats the apps' Swift and Kotlin with the rest of the tree,
and `mise run fmt:check` fails on what it would change, printing the diff;
`fmt:swift`, `fmt:kotlin` and their `:check`s are one language each, all
four through `.mise/appsfmt.sh`. The check is the writer run over a copy, so
the two cannot disagree. The CI job `android build` runs both checks.

- **Swift**: swift-format, configured once in `.swift-format` here, from the
  open-source Swift 6.4.2 the `android:*` tasks pin rather than Xcode's, whose
  swift-format is another version with other output. The settings are the
  ones that changed least of the code as it was written: four spaces,
  160 columns, the line breaks a writer chose kept, `#if` bodies and `case`
  labels not indented, spaces around `..<`, `case let .x(a)` and access on an
  extension left as written; imports sorted, and the rest of swift-format's
  default rules.
- **Kotlin**: ktfmt in the kotlinlang style, the `:ktfmt` task of the Gradle
  root (build-logic's `KtfmtConvention`), its version in
  `gradle/libs.versions.toml` and its jar locked and verified like every
  other artifact. Its width and indent are `.editorconfig`'s here, four
  spaces and 160 columns, which ktfmt reads over the root file's two-space
  default.

Each walks every `.swift`, or `.kt` and `.kts`, under `apps/` that git
tracks or would, so no build output is read, except a file whose first line
is `// Generated by …; do not edit`: the bridge's Kotlin and fingerprints
and kit-ui's `KitTokens.kt` are compared byte for byte with what their
generators write (`android:generate:check`, `DesignTokensKotlinTests`), and
Workouts' `BodyMapShapes.swift` is `scripts/body-map.py`'s.

## An app's app.json

Each app's folder holds an `app.json` that names the app once, as JSON so
every reader parses it with no dependency: the server's first-party reach
test (`internal/catalog/firstparty_reach_test.go`) reads the scopes and
asked-for packages of every app that asks for packages, and a Swift test holds each
app's manifest to its file (Sync's `ReachTests`, Workouts' `CoachTests`,
Chat's `AppJSON`, Tasks' `AppTests` and the template's
`TemplateAppTests`), so the two never drift. `mise run lint:apps` refuses an
app folder without one, or one missing a field below.

| Field | What |
| --- | --- |
| `id` | the app's folder name, which is also its bundle id's last label and the name `.mise/apps.sh` knows it by |
| `name` | its display name, the manifest's `appName`, the feeds' and the client document's |
| `platforms` | where it runs: `ios`, `macos`, `android`. A release ships a platform once its UI folder exists (`apple/`, `android/`) |
| `apple` | for an app that names `ios` or `macos`, the five fields below |
| `apple.bundleID` | the app's bundle id |
| `apple.scheme` | the scheme a release archives, a target of its `apple/targets.yml`; also its artifacts' name (`<scheme>-<version>-iOS.ipa`) |
| `apple.extensions` | the bundle ids of its extensions and widgets, empty where it has none |
| `apple.clientIDKey` | the Info.plist key a release stamps with its OAuth client id |
| `apple.redirectKey` | the Info.plist key a release stamps with the https redirect it claims |
| `android.applicationID` | for an app that names `android`: its application id, which its APK must carry and `assetlinks.json` names |
| `publishes` | the ids of the packages the app's site publishes from its `package/` folder (`.mise/closures.py`), which `.mise/apps.sh` lists in the authority document's entry for the app |
| `asks` | the packages its approval asks to have set up, each `{"package": <id>, "atLeast": <version>}` as the manifest's `package` details send them, in the manifest's order: the floor is the version the build was written against |
| `scopes` | the scopes it asks for, in the manifest's order |
| `icon` | its 1024-pixel icon, relative to the app's folder |
| `feed` | the folder `.mise/apps.sh` publishes its releases and feeds under, relative to `SUBSTRATE_APPLE_RELEASE_URL`; empty is the root, where the console's are, and no two apps share one |

An app publishes a package and asks for one apart: Workouts asks for
`substrate.reamde.dev/health`, which it does not publish, and for its own
two at the versions it carries. The details that name the device are not
in the file: Sync's `account` detail carries the phone's name and time
zone and its `webhook` detail the account it delivers under, so Sync's
manifest makes them per device in code, and `asks` holds only its packages.

The release reads every field but `asks` and `scopes`, which the
server's reach test and the manifests' tests hold.

## Third-party packages

What the apps take from outside this tree, each a decision with its
reason. `mise run lint:apps` refuses a package no row lists and a row
nothing takes, and holds the layering the rest of this page relies on
(its rules are the `# ---` sections of `.mise/appscheck.py`).

| Package | Why |
| --- | --- |
| `Sparkle` | the macOS updater every Mac app compiles in (`xcode/Shared/Updater.swift`): it reads the release's `appcast.xml` and checks its signature |
| `swift-crypto` | SHA-256 where CryptoKit is not, on Linux and Android, and taken on those platforms alone: SubstrateAuth's for PKCE, and ChatKit's for the hashed names its cache folder and files have always had |
| `swift-syntax` | the bridge's generator (`kit/Tools/BridgeGen`) reads the `Bridged` declarations with it; a tool's dependency only, never linked into an app |
| `com.squareup.okhttp3` | OkHttp, the transport on Android (`kit-device`): redirects off on every path, a line stream's included, and cancellation that reaches the socket |
| `com.google.crypto.tink` | Tink, the secure store's AEAD on Android: a keyset wrapped by an Android Keystore key, so what is on disk is ciphertext |
| `androidx` | AndroidX: DataStore, the secure store's ciphertext file; Compose (Material 3, its icons) and Activity, which kit-ui and the Gallery app draw with; and the test runners |
| `org.jetbrains.kotlinx` | kotlinx.serialization, which the generated Kotlin reads and writes bridged values with, and kotlinx.coroutines, the bridge's threads and flows |
| `com.facebook` | ktfmt, the Kotlin formatter `mise run fmt:kotlin` runs through the Gradle root's `:ktfmt` task, as its one self-contained jar; a tool's dependency only, never linked into an app |
| `org.jetbrains.kotlin` | the Kotlin and serialization Gradle plugins `build-logic` applies |
| `com.android.tools.build` | the Android Gradle Plugin |
| `junit` | JUnit 4, the Kotlin unit and instrumented tests' runner |
| `org.robolectric` | Robolectric, which runs kit-ui's composables on the JVM with Android's own graphics, so the gallery check draws every fixture with no emulator; chosen over Paparazzi because it is a test library alone, with no Gradle plugin reaching into AGP's variants |
| `io.github.takahirom.roborazzi` | Roborazzi, which writes what Robolectric drew as a PNG: kit-ui's half of `mise run apps:gallery` |

**Every Android artifact is checked by its sha256.** The Gradle locks
(`gradle.lockfile` beside each module, `settings-gradle.lockfile` and
`build-logic/`'s) pin each module's version, and
`gradle/gradle/verification-metadata.xml` pins its bytes: Gradle's
dependency verification, in its strict default, refuses any artifact, POM
or module file the file does not list with a matching sha256, plugins and
`build-logic`'s classpath included. A dependency change (a version in
`gradle/libs.versions.toml`, a new library, an AGP or Kotlin bump) is
followed by `mise run android:lock`, which rewrites the locks and then the
metadata from nothing, from what `android:build`, `android:test` and the
device tests resolve here in an empty Gradle home, as CI's runner resolves
them (Gradle verifies what it fetches, and a warm cache skips metadata a
cold resolution fetches), plus aapt2 for Linux, macOS and Windows, since
the Android plugin fetches the one for its host; commit both and read the
metadata's diff as a lock's: a changed checksum for a version that did not
change is a dependency that changed under its name. `mise run
lint:toolchain` holds the metadata to the locks (every locked module
listed, a sha256 for each of its files, metadata files verified, no
`<trust>` entry, aapt2 for Linux and macOS), so a lock change without it
fails the `lint` job before the `android build` one. Two downloads are not
Gradle's and so not in it: the Gradle distribution, which the wrapper
checks against `distributionSha256Sum`, and the `android-all` jars
Robolectric downloads itself at test time for kit-ui's gallery check,
outside Gradle's resolution and so outside this file.

Health data on a substrate

A walkthrough of the health-only (version 1) proposal in docs/plans/health-data.md; the all-domain version is docs/plans/observations.md for an engineer who wants to write health data into a substrate or build an app on top of it. Everything below is the substrate side: the records, the units, the reads. Providers (WHOOP, Oura, files) are mentioned only as the thing that writes.

Five ideas, in order

1. Every value says what it is

A stored number carries its form (instant, interval, counter or summary) and its unit. A nightly average is never confused with one reading.

2. One value type for measured numbers

quantity is {value, unit}: exact digits plus a UCUM code. The server converts kg to lb, never kg to litres, and never mg/dL to mmol/L on its own.

3. Small things are records, dense things are traces

A weighing or a night's sleep is one record. An hour of heart rate every 5 seconds is one trace record holding 720 values.

4. The server keeps a fast index it can always rebuild

Each trace and observation is unpacked into a narrow samples table plus 15-minute rollups. The changelog stays the truth; the index is a cache that replay reproduces.

5. One read answers "how did I sleep this month"

The records route gains an aggregate mode: pick a metric, a bucket, reducers, and get 30 rows of numbers instead of 30,000 records.

Version 2 of the plan (docs/plans/observations.md) widens this model to every measured thing and renames four things shown here: the forms instant and interval become gauge and amount; the trait and index are observed, observed_points and observed_rollups; every value gains an optional about (the thing observed, absent meaning you) and a code for categorical values; and the base kinds move to an observations package that health requires. Everything else on this page stands.

Names in this page use ada.example.com as the user's authority. A sample package imports under the user's own authority, so the kind health/observation is ada.example.com/health/observation for Ada and bob.example.com/health/observation for Bob.

Value forms

  
Every stored measurement carries a form. The form decides which reducers are legal and how two sources that overlap are combined. This is the one field that keeps a vendor's daily summary out of an average of raw readings.

Units and quantities

  
A quantity property holds {value, unit} and, where the kind allows it, a comparator. The value is always a string of exact digits. The unit is a UCUM code from a table the server owns.

  
weight:
  type: quantity
  dimension: mass            # kg, g, [lb_av] are admitted; anything else is refused
  units: [kg, "[lb_av]"]     # optional narrowing

# a value
weight: {value: "72.50", unit: kg}

  
Try it: convert, filter, refuse

  

    
    
  

  

  
The rules an app can rely on

  

    
RuleWhy

    
Conversion only inside one dimension (mass to mass, length to length)a unit table knows kg and lb; it does not know that glucose weighs 180.16 g/mol

    
mg/dL to mmol/L is a derivation, written as a second observation under a second LOINC code, stamped with the formula and versionthe molar mass belongs to the analyte, not the unit; the server never guesses it

    
HbA1c % to mmol/mol uses a method formula, not a ratioNGSP and IFCC are both dimensionless but differ by about 30 % if you treat them as a ratio

    
Temperature and temperature difference are two dimensionsa 0.3 °C deviation from baseline is 0.54 °F, not 32.54 °F

    
Arbitrary units ([IU]) convert to nothing except by prefixIU of insulin and IU of vitamin D are different things sharing a symbol

    
An unknown unit on a lab result is kept verbatim, not rejectedthe row still lists by date and code; normalizationFailure says why it has no canonical value

    
A comparator means "the true value is on this side"a stored <5 matches lt: 10, not lt: 3; it is counted but not averaged

  






  
Dense samples: traces

  
One record per sample would cost about 1 KB of changelog per sample. A trace packs one metric, from one source, over one fixed UTC period (an hour for continuous metrics, the session for a workout stream) into one record. The server computes the statistics on write and unpacks the values into the samples index.

  

    
    
  

  

    

    
What the engine does with it

  

  
Rules in one list

  
    
    
  • Identity is composed from source data, never minted: <provider>/<account>/<metric>/<period start>, never a sync page. Re-syncing with a different page size produces identical records.
    • 
    
  • Rewrites are normal (late data, corrections). A rewrite replaces the period whole and must carry a higher revision; a lower one is refused.
    • 
    
  • A trace is split where the UTC offset changes, so every sample knows its civil clock.
    • 
    
  • Size is bounded by sample count and bytes, so a day of 1 Hz data is not a valid period; an hour is.
    • 
    
  • You cannot filter on one sample inside a trace. A value you need to address on its own (a weighing, a lab result) is an observation.
    • 
  






  
Writing data

  
Three ways in, all through the ordinary write API. There is no health-specific endpoint.

  
1. One reading, from your app

  
PUT /api/v1/ada.example.com/health/observation/scale-2026-10-07T06:41
Authorization: Bearer <token>

{
  "properties": {
    "metric": "weight",
    "form": "instant",
    "value": {"value": "72.50", "unit": "kg"},
    "at": "2026-10-07T06:41:00Z",
    "utcOffset": 180,
    "source": "withings-body-plus",
    "recordingMethod": "automatic"
  }
}

  
A bare id after "metric": is accepted because the property is pinned to the metric kind; the server stores it as {"ref": "ada.example.com/health/metric/weight"}. Writing the same document twice changes nothing: an identical rewrite appends no changelog entry.

  
2. A vendor's daily number (a summary)

  
PUT /api/v1/ada.example.com/health/observation/whoop/george/9f2k/recovery

{
  "properties": {
    "metric": "whoop_recovery",
    "form": "summary",
    "statistic": "last",
    "period": "cycle",
    "periodId": "9f2k",
    "value": {"value": "71", "unit": "%"},
    "at": "2026-10-06T22:10:00Z",
    "endsAt": "2026-10-07T22:30:00Z",
    "utcOffset": 180,
    "source": "whoop-4",
    "origin": "providers.substrate.reamde.dev/whoop/recovery/whoop/george/9f2k",
    "revision": 4
  }
}

  
3. An hour of samples (a trace) from a function

  
host.effects.put(
    "ada.example.com/health/trace",
    f"oura/{account_id}/heart_rate/2026-10-07T06",   # ///
    properties={
        "metric": "heart_rate", "source": "oura-ring-gen3", "form": "instant",
        "at": "2026-10-07T06:00:00Z", "endsAt": "2026-10-07T07:00:00Z",
        "utcOffsetStart": 180, "utcOffsetEnd": 180,
        "unit": "/min", "interval": "PT5S",
        "values": ["61", "62", None, "60", ...],   # None is a gap
        "revision": 3,
        "origins": [heartrate_row_ref],
    },
)

  
What the server checks on every write

  
    
    
  • the unit is in the dimension the property declares; a wrong dimension is a 422 naming the unit
    • 
    
  • the form is legal for the kind, and a summary has a statistic and a period
    • 
    
  • a trace has exactly one timing form, ordered offsets inside the period, equal array lengths
    • 
    
  • a lab result sets exactly one of value, codedValue, ratio, text, absentReason
    • 
    
  • a lower revision than the stored one is refused
    •

Lists and single reads work as for any kind. The new thing is aggregate= on the records route: it reads the samples index (for a metric) or a numeric property (for any kind) and returns buckets of numbers. Build a request below and see the response shape.

Functions get the same read as host.records.aggregate(...) and an agent gets it through its query tool, so an assistant answers "how did I sleep this month" from 30 numbers.






  
Labs

  
A lab report is a labreport; each analyte is a labresult pointing at it. Lab values need more than a number: a comparator, coded answers, ratios, text, an absent reason, the lab's own ranges and flags, and a status that moves when a result is corrected.

  

  

  
What a trend view must do

  
    
    
  • Group by the metric's compatibility class (analyte, LOINC property, specimen, method), not by name: serum glucose in mg/dL and in mmol/L are two LOINC codes and one class; serum and whole-blood glucose are two classes.
    • 
    
  • Show the range that came with each result; the catalogue range is a labelled fallback.
    • 
    
  • Count bounded values (<0.3) but leave them out of averages, and say so.
    • 
    
  • A corrected result is the same record with status: corrected; the changelog keeps the old value.
    • 
  






  
Time and days

  
Every record carries a UTC instant and the UTC offset in force where the user was (utcOffset, in minutes). A "day" is then one of four things, and the request names which.

  

  

    
ModeRequestThat sample lands inUse for

    
Physical window{"every": "PT1H"}the 23:00 to 00:00 UTC hourcharts, intraday

    
Named zone day{"calendar": "day", "timezone": "Europe/Athens"}2026-03-30, a 23-hour dayreports in your home zone

    
Recorded-local day{"calendar": "day"}2026-03-30, because the sample's own offset says 02:30 localwhat the user experienced, even while travelling

    
Provider period{"records": {"kinds": ["ada.example.com/health/sleep"]}}whichever sleep or cycle spans itresting HR during sleep, WHOOP cycles, meals

  

  
    
    
  • Sleep belongs to the day you wake up: a sleep record declares dayAnchor: end.
    • 
    
  • Vendor days that start at 04:00 (Oura activity) use "offset": "PT4H" on a calendar bucket.
    • 
    
  • A sample with no offset is bucketed by the request's zone when one is named, and refused otherwise. Never by zero, never by the server's clock.
    • 
    
  • Two WHOOP cycles can share one calendar date; they stay two summaries because each carries its own periodId.
    •

# The Apple apps

The console, bundled, in a native shell for macOS, iPadOS and iOS: one
SwiftUI target (`Substrate`, bundle id `dev.reamde.substrate.console`) that
builds natively for both SDKs, not Mac Catalyst. The app carries its own copy
of `web/console/dist` and talks to a substrate only through its API, so any
substrate the user can reach works, whatever console that server serves.

```bash
mise run apple:install       # console + macOS app, installed in /Applications and opened
mise run apple:sim           # console + iOS app, on a booted (or the first) iPhone simulator
mise run apple:build         # console + the macOS app + the iOS simulator app
mise run apple:build:device  # console + the iOS app for a device, signed for the team's devices
mise run apple:project       # regenerate Substrate.xcodeproj, to open it in Xcode
mise run apple:release       # console + both apps, signed and published with their update feeds
```

The project file is generated by [xcodegen](https://github.com/yonaskolb/XcodeGen)
from `project.yml` and never committed. Signing is Xcode's automatic signing
for team `KFA5J8GDWJ`; the builds use the Apple Development identity and the
account signed in to Xcode, which `-allowProvisioningUpdates` registers the
app id and the device profile with. Nothing here runs in CI.

## How the console runs in it

The console only ever asks for same-origin paths, because the server serves
it at `/` with the API beside it. The shell keeps that true:
`ConsoleSchemeHandler` serves the bundled build at `substrate://console/` and
forwards the substrate's own paths (`/api/`, `/.well-known/`, `/healthz`, and
the auth door at the root when the request is not a navigation) to the chosen
server with `URLSession`, chunk by chunk, so the changefeed and an agent's turn
stream as they do in a browser. The server needs no CORS and the console no
base URL.

| Concern         | What the shell does                                                                     |
| --------------- | --------------------------------------------------------------------------------------- |
| Which server    | A native picker checks the address's discovery document first; the choice is remembered |
| Sessions        | One website data store per server: its token and console state stay with it             |
| The page's view | `window.substrateShell` (`{platform, server}`) is set before any script runs            |
| Links           | Anything outside `substrate://` opens in the system browser                             |
| `window.open`   | A provider's OAuth consent opens in the system browser, and its return lands there too  |
| Downloads       | The export lands in Downloads (macOS) or a share sheet (iOS)                            |
| macOS menus     | Change Server (⇧⌘,), Reload (⌘R), zoom (⌘0, ⌘+, ⌘−), Back and Forward (⌘[, ⌘])          |

The console's side is `web/console/src/lib/shell.ts`: the substrate's origin
and host come from the shell when there is one (a pasted record link, a bare
repository label completed at registration), the sign-in and register pages
name the server with a Change link, and Settings has a Server row. In a
browser there is no shell and none of it renders.

The macOS release build is sandboxed (`Support/Substrate-macOS.entitlements`:
network client, Downloads) with the hardened runtime. The debug build runs
outside the sandbox, for the driver below.

## Releases and updates

`mise run apple:release` (a pre-release; `apple:release stable` for a stable
one, from a clean tree) archives both apps, exports them, and publishes them
to `SUBSTRATE_APPLE_RELEASE_URL`: the path-style address of a folder on an S3
bucket that anyone may read and the key in `AWS_ACCESS_KEY_ID` /
`AWS_SECRET_ACCESS_KEY` may write. The address names a deployment, so it comes
from the environment, never from this tree.

```bash
SUBSTRATE_APPLE_RELEASE_URL=https://s3.example.com/public/projects/substrate/apple \
AWS_ACCESS_KEY_ID=… AWS_SECRET_ACCESS_KEY=… mise run apple:release
```

The version is the next patch after the last released one, plus the build
number and the commit, `0.113.1-pre.20261021.153012+ac85863e` (`.dirty`
when the tree was); the build number is the UTC time, so it only rises, and
it is what one release is compared to another by. The folder holds:

| Path                | What                                                                    |
| ------------------- | ----------------------------------------------------------------------- |
| `index.json`        | Every release, newest first; what the iOS app reads                     |
| `appcast.xml`       | Sparkle's feed; pre-releases ride its `prerelease` channel              |
| `index.html`        | The install page: an iPhone installs from it in Safari, a Mac downloads |
| `releases/<build>/` | The macOS zip, the IPA, its install manifest and icons, `release.json`  |

A released build carries the folder's address; a local build carries none
and never looks. On macOS, Sparkle checks every four hours and on Substrate →
Check for Updates, verifies the archive against the EdDSA key made on the
first release (kept in the login keychain under `substrate`; losing it means
every installed Mac app is replaced by hand once) and installs it. On iOS
only the system may install an app: the app reads `index.json` when it comes
to the foreground, at most hourly, and offers the newer release's install
link. Both include pre-releases when the running build is one; the Mac's app
menu turns that off.

Both are signed with the team's Apple Development identity, so the IPA
installs on the devices in the team's development profile (with Developer
Mode on) and the Mac app opens after Privacy & Security → Open Anyway once.
`SUBSTRATE_APPLE_EXPORT_IOS=release-testing` and
`SUBSTRATE_APPLE_EXPORT_MACOS=developer-id` switch to ad hoc and Developer ID
signing once those certificates exist.

## Driving a debug build

A debug build carries `DebugDriver`: it watches `automation/` in the app's
temporary directory, runs an `eval.js` found there in the page as an async
function body and writes the answer to `result.json`, and answers a `snap`
file with `snap.png`, the web view's snapshot. `SUBSTRATE_SHELL_SERVER` in
the environment starts it pointed at a server, past the picker.

```bash
# macOS
SUBSTRATE_SHELL_SERVER=http://localhost:8080 \
  web/apple/build/dd/Build/Products/Debug/Substrate.app/Contents/MacOS/Substrate &
dir="$(getconf DARWIN_USER_TEMP_DIR)automation"
echo 'return document.title' >"$dir/eval.js"; sleep 1; cat "$dir/result.json"

# a simulator: the app's data container
SUBSTRATE_SHELL_SERVER=http://localhost:8080 mise run apple:sim
dir="$(xcrun simctl get_app_container booted dev.reamde.substrate.console data)/tmp/automation"
```

Release builds carry none of it.

## Layout

```text
project.yml                 the xcodegen spec, the only project source
Support/                    Info.plist per platform, the macOS entitlements
Substrate/Assets.xcassets   the icon (scripts/icon.swift draws it)
Substrate/Sources/App/      the app, its macOS menus, ServerStore, the updater
scripts/feed.swift          a release's index.json, appcast.xml, install page and manifest
Substrate/Sources/Shell/    the scheme handler, the web view's controller, the picker, the debug driver
```

1. Verdict
The redesign lands the Paper direction: the collection grid, the record page, the tool page and the provider setup are calmer, denser and more legible than the old console, the dark theme is thorough, and the identity components (glyphs, record and actor marks, state words) make the whole thing feel like one product. Where the build followed a prototype page it is close to it. Where it had to invent (creating a record, reviewing a suggested change, writing history sentences about system objects, filtering by a state) it fell back to the data model and the developer's vocabulary, and those are the surfaces a non-technical person hits first when they try to 
do
 something rather than look. One crash (the task create form), one control that cannot work ("Always allow this"), and a create form built from native selects and raw enum values are the three things to fix before this merges; the first is the one critical finding, the other two lead the twelve major ones. The rest is a copy and consistency pass, then the parts of the purpose the build does not yet serve: seeing and changing what an agent may do, and seeing what a provider or an agent has done to your data from its own page.

2. What works, keep it
These are the decisions the rest of the console should be pulled toward, not away from.
keep
The record page as a document.
 Glyph, title, one meta line, a 36px property sheet, prose under a rule, then "Connected to", "Where it comes from", "Merged", "History". The sections have one heading recipe and the empty copy ("Nothing else points to this yet", "Only you have added to this. No provider fills it in.") is exactly the register the guide asked for.
keep
Inline editing for enums, states, references and lists.
 The enum popover, the "Move to → Done · fills in Completed at" state mover, the reference picker with "Showing the most recent. Type to search all people.", and the list editor with reorder, Add another and a keyboard legend are the best interaction work in the console.
keep
The tool page.
 "What it's allowed to do" as four plain cells, "When it runs", "Used by", "What it needs, and what it gives back", Try it with a result card ("Done. It changed nothing. Characters 44, Words 9"), and Recent runs. This is the clearest statement of the four purposes anywhere in the product.
keep
Provider setup.
 Four numbered steps with one action each, the redirect address with a copy button, accounts with "How it's doing", and confirmations that name the consequence ("Remove Google? This deletes the 0 records Google brought in…"). The "Waiting for Google" banner on a sync tool that links to "Finish setting up Google" is a good cross-link.
keep
The agent chat.
 Tool calls as one-line receipts ("Searched for "on-call handover", found 7 ✓"), suggestion cards with before → after and Apply / Edit first / Dismiss, the agent panel's "Can see / Can change / Tools it can use". It matches the prototype almost line for line.
keep
The dark theme and the token map.
 Every colour is a semantic token, kind hues have dark variants, soft fills are alpha so they sit on any surface. Nothing I opened broke in dark.
keep
Filters as full-size 
field | value | ×
 controls
 with "Clear all", the search box composed with them, and URL state for all of it.
keep
Empty and read-only states on collections.
 "No notes yet — Add the first one with New note, or ask an agent to." and, on a provider copy, "Google adds them here when it syncs." with the "read-only copies, kept up to date by Google" line and no New button.
keep
Nested tasks.
 The tree opens in place, "Today" due dates are amber, done rows grey their date, and the nesting switch is remembered per collection.
keep
History's live tail and four actor views
, and the record page's per-value history lines ("Priority: High → Urgent").

4. ⌘K and Search
major
K1
⌘K promises "Search or jump to…" but never shows a record
components/command-menu.tsx
Typing "lisb" offers one row, "Search your records for "lisb"", which leaves the palette for the Search page, and beneath it the four Google collections. They appear because cmdk's default filter matches letter subsequences: "Drive files" contains an l, an i, an s. No task named "Prepare travel for Lisbon" is offered, although the server answers a Words search in a few milliseconds.
Proposal.
 After a 150ms debounce, run the ranked read (Words mode, five hits) and show "Records" above "Collections" and "Pages", each hit as a 
RecordRef
 with its collection; keep the "Search your records" row last as the door to the full page. Replace the subsequence filter for collections and pages with word-prefix matching.
"lisb" in ⌘K: no records, and four collections matched by scattered letters.
minor
K2
The Search page mixes machinery into everyday results and explains ranking in engine terms
pages/search.tsx
, 
lib/search.ts:27-33
Searching "landing" on ada returns three tasks, then "recordpatchpolicy in Kinds", "substrate.reamde.dev/core/propose in Functions" and "person in Kinds". Those are internal kinds that the sidebar hides in everyday mode. The mode blurbs say "Both arms fused: the word ranking and the embedding similarity" and "spends one embedding call per search".
Proposal.
 Everyday scope = the primary kinds the sidebar lists; technical mode adds "Include the substrate's own records". Blurbs: Words "Matches the words you typed. Instant." · Words + meaning "Also finds records that mean the same thing, when a model is set up." · Meaning "Only by meaning. Needs a model, and each search calls it."

23. Open questions for the owner
The reference line on collection pages.
 The build shows it in everyday mode; the guide does not. Was that a deliberate change of mind, or drift? (S1)
Home's third section.
 The prototype had Recent chats; the build has Recent changes. Both, chats first? (H2)
The sign-in word.
 "Repository" is the model's word. Is "Your name" (with the address as helper) acceptable on the sign-in and register pages, or is the repository word part of the product's identity? (E2)
Saved views and Group by.
 They are in the approved prototype and not in the build. In scope for this redesign, or a later feature? (§20)
Apps built by agents.
 Today an agent's collections land in "Your data" flat, indistinguishable from samples. Should a package record the actor that declared it, so the console can say "Recipes · made by Notekeeper" and offer a package page with its kinds, its tools and its agent? That is an engine field, not a console change.
"Always allow this".
 The rule it writes cannot outrank a gate. Should the engine gain an exception form (an allow that names the gate it overrides), or should the control go? (M2)
The technical sidebar.
 Raw kind names only, as documented, or label with the name beside it? (X2)
Sidebar state.
 Shared through the preference record by design; is per-device acceptable? (S2)
Model keys.
 Is a console dialog for pasting an OpenAI key acceptable, or must a secret only ever be written through a record's own page? (G2)
Density.
 Should Compact reach the sidebar, lists and pickers, or stay a table setting? (E3)
